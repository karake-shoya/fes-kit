# 採算シミュレーション（損益分岐点＋AI診断）設計

2026-07-29 の壁打ちで決めた設計。実装は未着手。

## 背景（何が困っているか）

- レシピページで確認できるのは**原価率と1個あたり利益**だけ。「結局いくら儲かるのか」は分からない。
- 確かめる手段が**売上・実績記録ページに仮の数字を入れてみること**しかない。本来は当日の記録用の画面を電卓代わりに使っており、しかも入力が本物の実績データを汚す。
- そもそも**固定費を置く場所がない**ため、損益分岐点が計算できない。今の「利益」は材料費しか引いておらず、出店料5,000円を払っていても数字に出てこない。**実績ページの「実績利益」も同じ理由で実態より多く見えている**。

## 決めたこと

| 論点 | 決定 |
|---|---|
| 固定費の持ち方 | **専用の「かかるお金」画面**（`project_expenses` テーブル）。名前＋金額のリスト |
| 現実性の担保 | **想定来場者数をプロジェクト設定に持ち**、購入率の上限としてAIとコードの両方で判定 |
| パターンに含めるもの | **商品ごとの販売価格＋販売個数だけ**。固定費・原価はプロジェクト共通の最新値を使う |
| 非破壊 | `recipes.sellingPrice / servings` は触らない。パターンは別テーブル。「これにする」で明示的に書き戻す |
| AIの役割 | **計算はコード、判断はAI**。損益分岐点の逆算をAIにさせない（数字が信用できなくなる） |
| 複数商品の配分 | **今の「作る予定数」の構成比を保ったまま全体をスケール**する（段取りが崩れないため） |

## データモデル

```
project_expenses           かかるお金（個数に比例しない費用）
  id, projectId, label, amount, memo, createdAt, updatedAt
    例: 出店料 5000 / テントレンタル 3000 / ガスボンベ 1200

projects
  + expectedVisitors  integer nullable   想定来場者数

simulation_scenarios       採算パターン
  id, projectId, name, source ("manual" | "ai"), memo, createdAt
    例: A=自分で考えた案 / B=AI診断の案

simulation_items           パターンの明細（1商品1行）
  scenarioId, recipeId, sellingPrice, quantity   PK(scenarioId, recipeId)
```

- パターンは**1プロジェクト5件まで**（比較UIが破綻しないため）。
- 原価はパターンに保存せず**常に材料マスタの最新値で再計算**する。材料の単価を変えれば過去のパターンの利益も変わる — 「今の材料費だとこの案はどうなるか」を見る道具と割り切る。

## 計算ロジック（`src/lib/breakeven.ts` に純粋関数として置く）

記号: 1個あたり原価 `c_i`（= `calcRecipeCost().totalCost`）、販売価格 `p_i`、販売個数 `q_i`、
1個あたり利益 `m_i = p_i − c_i`、固定費合計 `F = Σ expenses.amount`。

```
利益 = Σ (m_i × q_i) − F
```

### ① 既存の価格でトントンになる販売個数

作る予定数の構成比 `r_i = servings_i / Σ servings` を保ったまま全体を `Q` 個にスケールする。

```
Σ (m_i × r_i × Q) = F   →   Q = F / Σ (m_i × r_i)
q_i = ceil(r_i × Q)
```

**必ず扱う異常系**（ここを落とすと嘘の数字が出る）:

- `Σ(m_i × r_i) ≤ 0`（全商品が赤字 or 利益ゼロ）→ 解なし。
  「今の価格では何個売っても回収できません。先に価格か材料を見直しましょう」と出す。
- `F = 0`（かかるお金が未登録）→ 0個でトントン。
  損益分岐点ではなく「かかるお金を登録すると計算できます」の案内に切り替える。
- `servings` が全て0 → 均等配分（`r_i = 1/n`）にフォールバック。
- 原価未登録（材料0件）のレシピは `m_i = p_i` になり利益を過大評価するので、**計算から除外して「原価未登録のため除外」と明示する**（実績ページの既存方針と揃える）。

### ② 購入率のチェック

```
購入率 = Σ q_i / 想定来場者数
```

100%超（来場者全員が1個以上買う前提）は機械的に警告する。AIの提案もこの検算を必ず通す。

## AI診断

既存の `src/actions/ai-price.ts`（`claude-haiku-4-5` ＋ `generateObject` ＋ Zod）と同じ作りで
`src/actions/ai-simulation.ts` を新設する。1商品ではなくプロジェクト全体を見る点が違う。

**渡すもの**: 商品ごとの（名前・原価・現在価格・現在の予定数）、固定費の内訳と合計、
想定来場者数、イベントの文脈（プロジェクト名・説明・イベント日）。

**返させるもの**: 商品ごとの推奨価格（10円単位）と推奨個数、全体の理由1〜2文。
**返させないもの**: 損益分岐点や利益額などの計算結果（コードで出す）。

**サーバー側で必ず検算する**:
1. 提案どおりの価格・個数で `Σ(m_i × q_i) − F` を計算し、赤字なら警告を添えて提示する（黙って採用しない）。
2. 購入率が100%を超えていたら警告する。
3. 提案価格が原価を下回っていたらその商品だけ除外して知らせる。

検算結果（実際の利益額・損益分岐点個数・購入率）は**常にAIの文章より目立つ位置**に出す。
`ANTHROPIC_API_KEY` 未設定時はAIボタンを隠し、①の計算だけで完結させる（既存の方針と同じ）。

## 画面

| 画面 | 内容 |
|---|---|
| `/projects/[id]/expenses`（新規） | かかるお金のCRUD。既存の `entity-form-dialog` と `swipe-action-card` をそのまま使う |
| `/projects/[id]/simulation`（新規） | 上: かかるお金の合計・想定来場者数・**今の価格なら何個でトントン**。下: パターン一覧（A/B比較）と「AIに相談する」 |
| プロジェクト設定 | 想定来場者数の入力を追加 |
| ホーム | 「あと◯個でトントン」カード（実績が入っていれば残り個数、なければ目標個数）＋ かかるお金への導線 |
| 売上・実績記録 | **実績利益から固定費を引いた「手残り」を追加**（現状の過大表示の解消） |
| レシピ一覧・詳細 | シミュレーション画面への導線 |

パターンの「これにする」は、明細の価格・個数を `recipes` へ一括更新（libSQL の batch）し、
`revalidateProject(projectId, "recipes")` を呼ぶ。

## 実装ステップ

1. スキーマ追加 → `npm run db:generate` / `db:migrate`
2. `src/lib/breakeven.ts` ＋ テスト（**先にテストを書く**。異常系が多く、数字が狂うと機能の意味がなくなるため）
3. かかるお金のCRUD（既存の共通部品の使い回しで済む）
4. シミュレーション画面（**AIなし・計算だけ**でまず完成させる）
5. パターンの保存・比較・反映
6. AI診断を上に乗せる
7. 実績ページに手残りを反映

4までで「損益分岐点が分かる」という価値は成立する。AIはその上の付加価値なので後回しでよい。

## 未決・保留

- 1人が複数個買う前提（購入率が100%を超えても妥当なケース）の扱い。まずは警告だけ出し、抑止はしない。
- パターンをメンバー間で共有するか（現状はプロジェクト単位なので自然に共有される）。
- 過去のイベントのパターンを次回に引き継ぐか（プロジェクト複製の話と合流する）。
